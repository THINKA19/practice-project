# 脚手架保护与参考代码使用规范

## 1. 目的与适用范围

本文供 AI 在本项目开发、复刻页面、提取函数、重构和代码检查时阅读并遵守，重点约束 `src/hooks/`、`src/utils/` 及其调用方。

核心原则：**优先复用脚手架已有能力，保护原有代码和文档；shared 仅供参考，禁止正式业务直接或间接依赖；新增实现必须由当前明确需求驱动，只提取必要代码，放入正式目录并完成实际接入。**

本文中的“文件”包括 TypeScript 代码、测试和 README 等说明文件。参考代码库可供阅读和借鉴，不等于已经接入项目的正式公共库。

本项目基于 unibest。AI 应先阅读项目 [AGENTS.md](../../AGENTS.md) 及相关 [Hermes 规范](../../hermes/README.md)，沿用现有请求、状态管理、路由和平台处理方式。本文补充参考代码使用边界，不另建一套工程规范。

## 2. 三类文件的职责

### 最小改动原则：非必要不修改

- 只修改完成当前明确需求所必需的文件、方法和调用点；能局部解决，就不扩大为模块或全项目改造。
- 优先复用现有实现，保留已有接口、目录结构和正常业务流程，不为了统一风格而重写代码。
- 不顺手重命名、批量格式化、整理无关注释、升级依赖、搬迁目录或修复范围外问题；发现问题可以说明，不默认纳入本次修改。
- 不为执行本规范预先增加检查脚本、插件、注册中心或配置改造。只有当前存在明确问题且必须通过这些改动解决时，才在授权范围内调整。
- shared 中没有实际业务需求的能力继续作为参考，不批量复制，不提前创建 project 目录或占位文件。
- 必要修改必须能说明当前问题、修改理由和调用影响；无法说明必要性的改动不实施。
- 验证针对实际改动开展。文档变更检查链接、表述和差异；功能变更执行相关测试与项目要求的检查，不借验证扩大修复范围。

### 2.1 脚手架原有代码和文档

- `src/hooks/` 中已有的 `useRequest.ts`、`useScroll.ts`、`useUpload.ts`、`useScroll.md` 等，以及 `src/utils/` 中原有工具，默认保留并优先复用。
- 不因个人偏好修改原有文件，不做与当前任务无关的重命名、搬迁、格式整理、注释重写或再次封装。
- 不把整套参考实现覆盖到脚手架原有目录，不用新工具替换已经正常工作的流程。
- 确需修改时，先说明具体缺陷或需求缺口、现有能力为何不能满足、拟修改范围和兼容影响；获得用户对该范围的确认后实施。用户已明确授权的同一范围不重复确认。
- 判断文件来源时结合当前源码、项目约定和历史记录，不把以后新增到正式目录的文件误认为脚手架原件。
- 不手改生成物；配置和生成方式遵循现有工程规范。

### 2.2 shared 参考代码

以下目录只作为参考资料：

- `src/hooks/shared/`
- `src/utils/shared/`

AI 可以阅读、比较和借鉴这些实现，但必须遵守：

1. 正式业务和正式公共代码禁止直接 import、动态 import 或通过 require 使用其中的实现。
2. 禁止通过统一导出、包装转发、自动导入、初始化注册等方式形成间接依赖。
3. 类型依赖也不能指向 shared；正式代码需要的类型应复用已有正式契约，或随必要实现一起定义。
4. 不因为参考目录提供了某个函数，就认为当前需求必须使用它。
5. 不为了让参考代码“有用武之地”而改动业务流程。
6. 参考库自身的测试可以引用参考代码，但不能用这些测试代替正式实现和业务接入验证。
7. 没有维护参考库的明确任务时，不顺手扩充、整理或修复整个参考库。

### 2.3 项目正式新增代码

- 跨页面复用的新增 Hook 放在 `src/hooks/project/`。
- 跨页面复用的新增通用工具放在 `src/utils/project/`。
- 仅服务某个页面或模块的逻辑，优先放在该页面或模块的局部 `composables/`、工具文件等既有位置，不过早提升为公共能力。
- 目录和文件按需创建，不提前建立空目录、完整工具体系或大量占位接口。
- 同一种正式能力只维护一份实现；新增前先检索已有正式代码。
- 正式代码独立维护，不依赖参考库后续同步，不要求参考实现与正式实现双向更新。

## 3. 新增前的判断顺序

AI 新增函数前必须明确：

1. 当前哪个页面、模块或业务流程需要它？实际调用方在哪里？
2. 脚手架或已有正式实现为什么不能直接满足需求？
3. 当前最小需要哪些参数、返回值、行为和平台支持？

不能回答上述问题时，不新增该能力。执行顺序为：**已有正式能力 → 当前页面的简单局部实现 → 有明确复用需求的新增公共实现**。

不得以“以后可能需要”“让架构完整”“参考库已经有了”为理由，提前加入无调用方的函数、配置项、注册中心或抽象层。用户明确要求建设独立公共库时，按该任务另行确定范围。

## 4. 从参考代码提取正式实现

提取的是当前需求所需的实现，不是整套文件或目录。

1. 阅读相关参考函数及其依赖，确认与本项目需求是否一致。
2. 只提取必要方法及其最小依赖；删除与本次需求无关的分支和扩展能力。
3. 如果一个简单需求会带入大量依赖，重新评估是否直接实现更简单，不沿依赖链复制整套基础设施。
4. 适配本项目现有 API、HTTP、Pinia、路由、页面生命周期及条件编译约定。
5. 对通用方法只保留通用机制；业务路径、兜底目标、提示策略等由调用方提供。
6. 为正式实现提供真实调用点，确认没有遗留对 shared 的直接或间接依赖。
7. 补充必要的回归验证，测试正式实现而非参考副本。

禁止另建第二套请求封装、登录状态、持久化或路由体系来配合参考实现。普通平台调用可以继续使用项目允许的 uni API，不要求业务统一经过一层新增包装。

正式文件应保留准确的文件用途说明；导出方法提供方法级 JSDoc，说明参数、返回值、使用示例以及适用的平台和行为限制。复杂实现可注明参考来源，但不能复制与实际能力不符的大段介绍。

## 5. 提取示例

需求：某个订单页面需要一个共用倒计时时钟。

- 先检查已有正式能力是否满足需求。
- 若只在该页面使用，放在页面局部逻辑中；确需跨页面复用时，再新增 `src/hooks/project/useCountdown.ts`。
- 可以参考 `src/hooks/shared/useCountdown.ts`，只提取需要的时钟、启停和清理逻辑。
- 正式页面引用正式实现，并按页面显示、隐藏和销毁生命周期接入。
- 不同时复制分页、Tab 筛选、事件总线、存储、音频或支付工具。
- 不创建一个从 shared 转发导出的文件来冒充正式实现。

## 6. 自动导入、构建与检查边界

禁止手动 import 并不足以保证参考代码不被使用。AI 应检查自动导入扫描、统一导出、动态加载和初始化入口是否把 shared 带入正式依赖链。

必须区分两件事：

- **业务依赖隔离**：正式代码不能直接或间接使用 shared，这是本文要求。
- **工具扫描隔离**：参考文件是否参与构建扫描、类型检查或测试发现，取决于实际配置，不能仅靠本文保证。

shared 位于 `src` 下，不代表一定被打进运行包，也不代表已被工具排除。必须根据配置和依赖证据判断。发现违规引用或扫描风险时，说明位置、影响和最小修正方案；不以此为由自行重写脚手架配置或搬迁整个目录。

## 7. AI 工作流程与交付要求

1. 阅读当前任务相关约定，确认用户授权范围；仅要求分析或写文档时，不修改业务代码。
2. 检查工作区现有改动，保护用户修改。
3. 检索已有正式实现，确定实际需求与调用方。
4. 必要时阅读 shared，只选取当前需求所需能力。
5. 在正式位置实现并完成接入，保留原有脚手架边界。
6. 检查平台行为、生命周期、依赖方向和错误处理；涉及异步状态时检查迟到响应、取消与清理。
7. 使用 pnpm 执行适当的检查，遵循项目现有合入门禁；已有失败如实记录，不擅自扩大修复范围。
8. 交付说明新增或修改了哪些文件、实际调用方、是否改动脚手架、验证结果和未验证项。

只增加一批工具文件、没有完成当前业务接入，不能宣称业务任务已经完成。参考测试通过、局部测试通过，也不能表述为全项目或真机验证通过。

## 8. 文档定位与现有状态

本文是上述约束的集中说明。shared 内的 README 只说明参考用途和能力范围，有关使用边界统一引用本文，不重复维护整份规则。

文档约束不等于技术隔离已经完成。不得因本文存在就宣称已迁移代码、清理引用或调整构建配置；需要落实这些变化时，先检查当前状态，再按最小改动原则处理。

项目 AGENTS.md 已将本文列为开发前必读入口。能够读取该入口的 AI 应继续阅读本文；不读取项目指引的外部工具仍需显式提供本文。维护时保留链接，不复制多份正文。
