# 脚手架保护与参考代码使用规范

## 1. 目的与适用范围

本文供 AI 在本项目开发、复刻页面、提取函数、重构和代码检查时阅读并遵守，重点约束 `src/hooks/`、`src/utils/` 及其调用方。

核心原则：**优先复用脚手架已有能力，保护原有代码和文档；docs/reference 中的历史 shared 代码仅供参考，禁止正式业务直接或间接依赖；新增实现必须由当前明确需求驱动，只提取必要代码，放入正式目录并完成实际接入。**

本文中的“文件”包括 TypeScript 代码、测试和 README 等说明文件。参考代码库可供阅读和借鉴，不等于已经接入项目的正式公共库。

本项目基于 unibest。AI 应先阅读项目 [AGENTS.md](../../AGENTS.md) 及相关 [Hermes 规范](../../hermes/README.md)，沿用现有请求、状态管理、路由和平台处理方式。本文补充参考代码使用边界，不另建一套工程规范。

## 2. 三类文件的职责

### 最小改动原则：非必要不修改

- 只修改完成当前明确需求所必需的文件、方法和调用点；能局部解决，就不扩大为模块或全项目改造。
- 优先复用现有实现，保留已有接口、目录结构和正常业务流程，不为了统一风格而重写代码。
- 不顺手重命名、批量格式化、整理无关注释、升级依赖、搬迁目录或修复范围外问题；发现问题可以说明，不默认纳入本次修改。
- 不为执行本规范预先增加检查脚本、插件、注册中心或配置改造。只有当前存在明确问题且必须通过这些改动解决时，才在授权范围内调整。
- shared 中没有实际业务需求的能力继续作为参考，不批量复制，不提前创建 project 目录或占位文件。
- 必要修改必须能说明当前问题、修改理由和调用影响；无法说明必要性的改动不实施。
- 验证针对实际改动开展。文档变更检查链接、表述和差异；功能变更执行相关测试与项目要求的检查，不借验证扩大修复范围。

### 2.1 脚手架原有代码和文档

#### Store：稳定基础与兼容入口，非必要禁止修改

- `src/store/**` 已完成唯一会话兼容收敛，定位为稳定的基础设施与历史调用入口。普通业务任务禁止新增、修改、删除、搬迁或格式化其中的代码、测试和说明文件；不得向这里继续添加业务 Store、业务 API 或权限规则。
- `index.ts` 仅安装 Pinia、持久化插件并导出既有兼容入口；保留提前激活 Pinia 的平台兼容行为。`token.ts` 仅提供既有凭证读取、时间更新、刷新和本地清理；`user.ts` 仅提供只读资料、资料刷新及会话清理。两者不是独立 Pinia Store，不维护或持久化第二份 Token、身份或用户资料，也不恢复登录方法和任意资料 setter。
- 唯一共享会话归 `src/pages/auth/session/`：负责身份校验、会话提交、恢复、刷新和退出。新业务通过该模块公开入口访问，不直接读写其内部 Store。各端登录模块负责凭证交换；用户资料编辑归资料业务模块。
- 购物车、订单、门店上下文、商家权限、骑手任务等状态归所属业务模块；跨页面使用不构成移入根级 `src/store/` 的理由。不得通过新的全局 Store、持久化键或兼容转发绕过唯一会话边界。
- `token.logout` 与 `user.clearUserInfo` 都只清理整个本地会话，避免 HTTP 401 清理再次发起注销请求；用户主动退出使用 Session 的 `logout`。不得只清资料而保留凭证，也不得把清理方法当作资料编辑接口。
- 仅在已确认的基础设施缺陷、脚手架接口变化，或旧调用全部迁移后的兼容清理确有必要时，先说明证据、调用影响和验证范围，并取得用户对该范围的明确授权后调整；同一已授权范围不重复确认。不因普通业务需求、风格统一或预想能力放宽边界。
- 必要变更验证三端状态一致、凭证到期、刷新合并、退出及换身份后的迟到响应、只读资料和持久化恢复；Store 测试统一放在 `src/store/__tests__/`。局部测试通过不等于全量门禁、真实服务或设备验证通过，历史路由测试缺口和公共请求限制应如实记录。
- 本节为保护规则唯一正文，`AGENTS.md`、Hermes 与模块说明引用本节。普通业务任务不得删除或放宽本节，明确授权的规范维护除外。

#### Router：禁止修改

- `src/router/**` 整个目录为受保护的脚手架路由基础，禁止新增、修改、删除、搬迁或格式化任何文件，包括配置、实现、类型、测试和 README。
- 此规则不适用下文“确需修改时确认”的普通例外。不得以业务接入、修复编译或统一架构为由修改该目录；发现公共路由缺口应记录证据，交由用户单独决定，不在业务任务中放宽规则。
- 保留 `main.ts`、`App.vue` 对现有路由的正常接入；禁止通过复制第二套路由拦截器、覆盖全局 uni 导航 API、替换或卸载现有拦截器绕过保护。
- 订单、商品、商家门店权限、骑手准入、业务提示及业务回跳目标由所属模块维护。共享身份检查和三端登录路径由 `src/pages/auth/session/` 维护，不向 `src/router/` 添加业务规则或业务路径文件。
- 页面路径常量归各端现有 `routes.ts`；新增页面沿用现有页面注册生成机制，不手改生成的 `src/pages.json`。页面登录需求优先使用已有 `definePage` 元数据，并核对当前黑白名单语义及平台适用范围。
- 通用导航只执行路径编码、平台导航方式选择等机制，不决定业务目标。业务访问检查应覆盖页面直接进入和敏感动作；页面与按钮检查不能替代服务端授权。
- 交付前核对 `src/router/**` 与任务开始时内容一致；不得回滚已有用户改动。规则正文仅在本文维护，其他入口引用本文。

#### OpenAPI-generated service: do not edit manually

- `src/service/**` is scaffold-owned OpenAPI-generated output, not a business service layer. Do not manually add, edit, delete, move, or format its files during ordinary business development.
- Business API calls and response models belong to the owning business module's `api/` and `models/` directories and must reuse the existing public HTTP client. Do not introduce new business dependencies on the scaffold's generated example endpoints.
- `pnpm openapi` reads `openapi-ts-request.config.ts` and writes to `src/service/`. The current configuration points to a unibest test schema. Do not run this command or replace its schema/output settings as part of unrelated business work.
- If generated API integration is explicitly requested, review the schema source, request-client compatibility, output ownership, and affected consumers first. Update the generation source/configuration and regenerate within that authorized scope; never patch generated output by hand or modify protected HTTP/router code to make it work.
- Keep the existing files unless scaffold cleanup is explicitly requested. No current consumer does not by itself authorize deleting the directory, generator configuration, script, or dependency. Verify that generated output is unchanged when delivering ordinary business changes.

#### HTTP 与公共 Mock：业务开发禁止修改

- 根级 `src/api/` 已取消，禁止重建，禁止新增其中的接口、类型、Mock、转发或兼容占位文件。接口和类型归所属业务模块的 `api/`、`models/`；业务模块自己的 `api/` 目录继续使用。受保护 HTTP 中既有的 `@/api/types/login` 仅为历史类型引用，由 TypeScript 精确路径映射到 session 正式类型，不恢复物理目录，新业务禁止引用该旧路径。

- `src/http/**`、`src/mock/**` 是受保护的公共基础，包括实现、类型、测试和 README。业务开发、登录接入、页面复刻和修复业务错误均禁止新增、修改、删除、搬迁或格式化这些目录中的文件。
- 本保护规则不适用上面“确需修改时确认”的普通例外。不得以完成业务、修复编译、接通 Mock 或统一架构为理由修改公共 HTTP/Mock；发现缺口应记录具体证据并交由用户单独决定。
- 禁止在目录外复制第二套请求实现，或通过覆盖请求方法、响应回调、全局 uni API、修改公共模块内部状态等方式绕过保护。不得为避开保护新增 `src/app/http.ts` 等请求转发层。
- 业务接口、参数和返回值转换、身份与权限规则放在所属业务模块；共享会话逻辑归 `src/pages/auth/session/`。公共请求依赖的既有 `src/store/token.ts` 和类型路径仅保留兼容入口，不创建第二份 Token 状态。
- 业务 Mock 放在所属模块的 `mock/`，通过已有 `entry.mock.ts` 发现规则登记；不得修改公共加载器、匹配规则和响应协议来迁就业务数据。公共 Mock 与业务 Mock 的修改范围必须区分。
- 允许使用公共能力已有的参数和配置接口。开发 Mock 的适配器在 `src/http/alova.ts` 创建既有实例时依据原有开关配置一次；`src/main.ts` 和全局测试初始化不再改写请求适配器。本次接入位置调整为用户明确授权的基础设施维护，不放宽普通业务对 HTTP/Mock 的保护限制。不复制请求实现、不覆盖认证或响应回调、不增加业务转发入口。模块缓存策略由各业务请求显式声明。
- 保护规则正文仅在本文维护，其他文档引用本文，不得在业务任务中删除或放宽这些限制。交付前核对公共目录内容与任务开始时一致；已有用户改动不得回滚。

- `src/hooks/` 中已有的 `useRequest.ts`、`useScroll.ts`、`useUpload.ts`、`useScroll.md` 等，以及 `src/utils/` 中原有工具，默认保留并优先复用。
- 不因个人偏好修改原有文件，不做与当前任务无关的重命名、搬迁、格式整理、注释重写或再次封装。
- 不把整套参考实现覆盖到脚手架原有目录，不用新工具替换已经正常工作的流程。
- 确需修改时，先说明具体缺陷或需求缺口、现有能力为何不能满足、拟修改范围和兼容影响；获得用户对该范围的确认后实施。用户已明确授权的同一范围不重复确认。
- 判断文件来源时结合当前源码、项目约定和历史记录，不把以后新增到正式目录的文件误认为脚手架原件。
- 不手改生成物；配置和生成方式遵循现有工程规范。

### 2.2 历史参考代码

以下目录只作为参考资料：

- `docs/reference/hooks/`：原 src/hooks/shared 的组合式函数参考。
- `docs/reference/kernel/`：原 src/utils/shared/kernel 的工具参考。
- `docs/reference/platform/`：原 src/utils/shared/platform 的平台参考。

这些目录不属于正式能力或自动测试集；不在 src 下保留旧副本或兼容导出。

AI 可以阅读、比较和借鉴这些实现，但必须遵守：

1. 正式业务和正式公共代码禁止直接 import、动态 import 或通过 require 使用其中的实现。
2. 禁止通过统一导出、包装转发、自动导入、初始化注册等方式形成间接依赖。
3. 类型依赖也不能指向参考目录；正式代码需要的类型应复用已有正式契约，或随必要实现一起定义。
4. 不因为参考目录提供了某个函数，就认为当前需求必须使用它。
5. 不为了让参考代码“有用武之地”而改动业务流程。
6. 参考库自身的测试可以引用参考代码，但不能用这些测试代替正式实现和业务接入验证。
7. 没有维护参考库的明确任务时，不顺手扩充、整理或修复整个参考库。

### 2.3 项目正式新增代码

- 跨页面复用的新增 Hook 放在 `src/hooks/project/`。
- 跨页面复用的新增通用工具放在 `src/utils/project/`。
- 仅服务某个页面或模块的逻辑，优先放在该页面或模块的局部 `composables/`、工具文件等既有位置，不过早提升为公共能力。
- 目录和文件按需创建，不提前建立空目录、完整工具体系或大量占位接口。
- 同一种正式能力只维护一份实现；新增前先检索已有正式代码。
- 正式代码独立维护，不依赖参考库后续同步，不要求参考实现与正式实现双向更新。

### 2.4 提取后的旧代码处置

新增正式实现后必须检查旧实现，避免同一种正式能力存在两个可选入口。不能仅因文件同名就删除，也不能因为“以后可能用到”永久保留重复运行代码。

1. **完整替代的旧正式实现**：迁移全部调用方后，删除旧文件及无用导出、对应旧测试和失效说明。无明确兼容需求，不保留旧名称别名或转发层。
2. **部分提取的参考实现**：正式目录仅保留当前必需能力；有保留价值的参考代码按内部依赖整体迁到 `docs/reference/<主题>/`，不在 `src` 留副本。不要逐个挖掉重叠函数，造成参考模块或其测试断裂。
3. **无保留价值的参考代码**：确认调用和内部依赖后删除，可通过 Git 历史追溯，不额外建立备份目录。
4. **仍有调用的旧代码**：先确认调用属于正式业务还是参考模块，再迁移、保留或连同依赖一起处理；不凭文件名相似直接删除。不为了删除旧文件而把全部未使用功能搬到正式目录。
5. **依赖与入口**：正式代码不得 import、转发导出或通过自动扫描间接依赖 `docs/reference`；参考代码也不通过调用新正式工具来维持两套实现的同步。无调用方的参考统一导出入口应清理。
6. **检查与文档**：检查路径别名、相对引用、测试、自动导入、构建、类型检查和 lint 的实际扫描范围。历史测试随参考迁出，只作为资料；必要的行为测试应在正式实现旁维护。README 标明正式入口、参考范围和未迁移能力，长期规则仅维护在本文。
7. **执行边界**：用户已授权提取或清理时，按已确认范围完成旧代码处置；仅做分析时不删除。一次只清理本次相关主题，不顺手搬迁其他参考库。

当前 hooks、kernel、platform 参考已统一迁到 [docs/reference](../reference/README.md)。正式导航和基础反馈位于 src/utils/project/，其他参考能力未因此自动成为正式能力。当前 TypeScript/Vitest 的 src 扫描边界排除参考目录，ESLint 显式忽略 docs/reference/**；自动导入仍扫描正式 src/hooks，迁出后不会扫描历史 hooks。

## 3. 新增前的判断顺序

AI 新增函数前必须明确：

1. 当前哪个页面、模块或业务流程需要它？实际调用方在哪里？
2. 脚手架或已有正式实现为什么不能直接满足需求？
3. 当前最小需要哪些参数、返回值、行为和平台支持？

不能回答上述问题时，不新增该能力。执行顺序为：**已有正式能力 → 当前页面的简单局部实现 → 有明确复用需求的新增公共实现**。

不得以“以后可能需要”“让架构完整”“参考库已经有了”为理由，提前加入无调用方的函数、配置项、注册中心或抽象层。用户明确要求建设独立公共库时，按该任务另行确定范围。

## 4. 从参考代码提取正式实现

提取的是当前需求所需的实现，不是整套文件或目录。

1. 阅读相关参考函数及其依赖，确认与本项目需求是否一致。
2. 只提取必要方法及其最小依赖；删除与本次需求无关的分支和扩展能力。
3. 如果一个简单需求会带入大量依赖，重新评估是否直接实现更简单，不沿依赖链复制整套基础设施。
4. 适配本项目现有 API、HTTP、Pinia、路由、页面生命周期及条件编译约定。
5. 对通用方法只保留通用机制；业务路径、兜底目标、提示策略等由调用方提供。
6. 为正式实现提供真实调用点，确认没有遗留对 shared 的直接或间接依赖。
7. 补充必要的回归验证，测试正式实现而非参考副本。

禁止另建第二套请求封装、登录状态、持久化或路由体系来配合参考实现。普通平台调用可以继续使用项目允许的 uni API，不要求业务统一经过一层新增包装。

正式文件应保留准确的文件用途说明；导出方法提供方法级 JSDoc，说明参数、返回值、使用示例以及适用的平台和行为限制。复杂实现可注明参考来源，但不能复制与实际能力不符的大段介绍。

## 5. 提取示例

需求：某个订单页面需要一个共用倒计时时钟。

- 先检查已有正式能力是否满足需求。
- 若只在该页面使用，放在页面局部逻辑中；确需跨页面复用时，再新增 `src/hooks/project/useCountdown.ts`。
- 可以参考 `docs/reference/hooks/useCountdown.ts`，只提取需要的时钟、启停和清理逻辑。
- 正式页面引用正式实现，并按页面显示、隐藏和销毁生命周期接入。
- 不同时复制分页、Tab 筛选、事件总线、存储、音频或支付工具。
- 不创建一个从 shared 转发导出的文件来冒充正式实现。

## 6. 自动导入、构建与检查边界

禁止手动 import 并不足以保证参考代码不被使用。AI 应检查自动导入扫描、统一导出、动态加载和初始化入口是否把 shared 带入正式依赖链。

必须区分两件事：

- **业务依赖隔离**：正式代码不能直接或间接使用 shared，这是本文要求。
- **工具扫描隔离**：参考文件是否参与构建扫描、类型检查或测试发现，取决于实际配置，不能仅靠本文保证。

参考代码即使放在 src 外，也不代表可以省略依赖检查。必须根据配置和依赖证据判断。发现违规引用或扫描风险时，说明位置、影响和最小修正方案；不以此为由自行重写脚手架配置或搬迁整个目录。

## 7. AI 工作流程与交付要求

1. 阅读当前任务相关约定，确认用户授权范围；仅要求分析或写文档时，不修改业务代码。
2. 检查工作区现有改动，保护用户修改。
3. 检索已有正式实现，确定实际需求与调用方。
4. 必要时阅读 shared，只选取当前需求所需能力。
