# 常用功能

正式目录按当前业务命名：scan-result（扫码核销）、sign-in（每日签到）、booking（预约订座）、bill-pay（优惠买单）。个人中心入口使用 src/pages/routes.ts，页面按 definePage 自动注册。

已对比并清理原 often、often7 参考副本：签到日志日期匹配、预约联系人/人数/十分钟时段、优惠两列卡片与确认弹层均由当前正式模块维护，不保留第二套业务代码。旧示例的固定余额、生成核销成功结果和预约本地成功提示不作为正式能力。

核销复用 pickup1/scan-result 的公开订单 API；真实授权由后端决定。签到、预约、买单的请求与模型各归所属模块。未提供真实支付契约，买单仅在开发 Mock 下模拟，生产禁用提交。

## 三项业务的异常处理

- 扫码核销：纯核销码或带唯一 hxNumber 参数的二维码 → 查询 → 核对订单 → 确认。提交失败或超时不代表服务端未处理，必须重新查询后才能再次核销。二维码地址只用于提取参数，不执行导航。
- 每日签到：日志严格校验；当天成功提交后保留当前账号的日期确认，即使后续日志刷新失败，也不会再次开放签到。提交异常先查询日志确认，日志仍失败时提示重载。日期在操作时更新，不提供补签或客户端积分发放。
- 优惠买单：优惠加载完成后才能生成确认单；提交使用确认时的消费金额快照；同金额关闭后重试沿用请求号，避免网络结果不明时生成新单；返回实付与确认金额不一致时不展示完成。优惠为单条最优满减，不叠加。

这些处理不等同于真实业务联调完成。核销仍需后端核对员工所属门店及具体核销权限，现有取餐 Mock 的账号隔离不能证明员工核销与顾客取餐列表联动。签到积分与业务日以服务端为准。真实买单还缺门店上下文、服务端报价及订单、支付回调和订单状态查询契约；当前保持模拟模式。

## 本轮流程收敛

composable 入口使用 useBooking、useVerify、useSign、useBill、useDiscounts，文件与函数同名，不保留旧别名。
预约活动配置提供加载状态及失败重试；人数越界拒绝提交，不静默替换。只有 accepted=true 表示申请已接收，不代表真实占座。
预约提交后结果不确定时，当前页面阻止重复提交并提示联系门店核对；缺少服务端幂等与查询契约，重进页面不能保证去重。
模拟买单结果不确定时不能改金额创建新请求，原金额重试复用请求号；页面重建后的恢复仍需真实订单契约。
